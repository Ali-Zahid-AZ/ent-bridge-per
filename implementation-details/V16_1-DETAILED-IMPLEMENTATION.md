### 23.1.0 Architecture Overview

**The problem (split-brain pattern — REJECTED):** The original V16-1 proposal patched `person_resolver.py` to load `email-urls.csv` as a secondary data source and created a separate scratch backfill script for Neo4j. This violated the "Single Source of Truth" principle — `math_schema.parquet` is the canonical data store for all downstream consumers (`person_resolver.py`, XGBoost, Bayesian engine, ensemble forecaster). Adding a secondary load path created a split-brain dependency.

**The solution (upstream ETL join — ACCEPTED):** Join `email-urls.csv` into the Polars DataFrame during `ingest_data()` in `ingest_only_full.py`, BEFORE `math_schema.parquet` is written. This follows the exact same pattern as `reconstruct_taxonomy()` which already joins taxonomy classifications onto the raw DataFrame during ingestion. Four insertion points, all in `ingest_only_full.py`.

**Data flow:**

```
1. CSV loaded (190,926 rows, 326 columns, no Email column)
2. Ghost column purge (removes columns with >85% null rate)
3. [V16-1 INSERTION A] Join email-urls.csv on Lead_ID → df gains email column
4. Math schema extraction → math_schema.parquet gains email column
5. Graph extraction → Neo4j Lead nodes gain email property
6. [ZERO CHANGES] person_resolver.py auto-detects email in parquet → Tier 1 matching
```

**What this enables:** After re-ingestion, `person_resolver.py` finds the `email` column in `math_schema.parquet` and runs Tier 1 (exact email matching) on 11,386 leads. Combined with Tier 2 (phone matching) on remaining ~179K leads, the dual-identifier identity resolution pipeline is operational for the first time.

### 23.1.1 Insertion Point A — Email Join (after ghost column purge, before math extraction)

**TARGET ARTIFACT (MODIFY):** `/home/az/Downloads/testing-delete/p-ai-paid-marketing/src/etl/ingest_only_full.py`

**LOCATION:** In `ingest_data()`, after the sanitization block complete message and BEFORE the math route data preparation section. The exact line sequence is:

```
Line 306:         print(f"Purged {len(cols_to_drop)} ghost columns.")
Line 308:     print(f"Sanitization complete. Current shape: {df.height} rows, {df.width} columns.")
Line 309:     # ==========================================
Line 311:     # Math route data preparation
```

**INSERT after line 308** (after `print("Sanitization complete...")`) and **before line 311** (`# Math route data preparation`):

```python
    # V16-1: Join recovered emails from unstructured column mining
    # Data source: data/raw/email-urls.csv (11,386 leads, 13,502 rows)
    # Generated by full-column @-scan of leads-data-191K.csv on 2026-05-29
    email_csv = os.path.join(project_root, "data/raw/email-urls.csv")
    if os.path.exists(email_csv):
        try:
            email_df = pl.read_csv(email_csv).filter(
                pl.col("email") != ""
            ).select(
                ["Lead_ID", "email"]
            ).unique(subset=["Lead_ID"], keep="first")
            df = df.join(email_df, on="Lead_ID", how="left")
            print(f"  [V16-1] Joined {email_df.height} recovered emails from email-urls.csv")
        except Exception as e:
            print(f"  [V16-1 Non-Critical] Email join failed: {e}")
    # END V16-1
```

**ARCHITECTURAL RATIONALE:**

1. **Why this position (after purge, before extraction):** The ghost column purge drops any column with >85% null rate. If the email join happened BEFORE the purge, the email column (94% null, 6% filled) would be deleted by the purge filter. Placing the join AFTER the purge ensures the email column survives. The math schema and graph extraction both happen after this insertion point, so email flows into both `math_schema.parquet` and Neo4j.
2. **Why `os.path.exists` guard:** `email-urls.csv` may not exist if the column mining step was never run or the file was deleted. The pipeline must NOT crash on a missing optional data source. This is a non-critical augmentation — not a hard dependency.
3. **Why `try/except Exception`:** Polars can fail on malformed CSV, encoding issues, or schema mismatches. The pipeline continues with a warning — email resolution is additive, not critical.
4. **Why `how="left"`:** Preserves all 190,926 leads in the original DataFrame. Rows without a matching email (the ~179K majority) get a null `email` value. This matches the existing taxonomy join pattern.
5. **Why `unique(subset=["Lead_ID"], keep="first")`:** `email-urls.csv` contains one row per `(Lead_ID, email, source_column)` template — a single Lead_ID may have multiple rows if email was found in multiple source columns. We take the first occurrence. The semantics of "first" are undefined in Polars (order-dependent), but this is acceptable since all rows for the same Lead_ID contain the same email address (the extraction deduplicated by email within each source column).

### 23.1.2 Insertion Point B — Email in Math Schema

**LOCATION:** In `ingest_data()`, the `math_columns` list at line 313-334.

**ADD `"email"`** to the `math_columns` list:

```python
    math_columns = [
        "Lead_ID",
        "STATUS",
        ...
        "CREATEDDATE",
        "email",          # V16-1: recovered from unstructured columns
    ]
```

**LOCATION:** In the math extraction processing loop at line 339-341:

```python
    for col_name in available_math_cols:
        if col_name in ["Lead_ID", "CITY", "STATUS", "COUNTRY"]:
            continue
```

**MODIFY to:**

```python
    for col_name in available_math_cols:
        if col_name in ["Lead_ID", "CITY", "STATUS", "COUNTRY", "email"]:
            continue
```

**ARCHITECTURAL RATIONALE:**

1. **Why `email` must be in `math_columns`:** Without it, `math_schema.parquet` won't contain the email column, and `person_resolver.py` won't find it. The math schema is the canonical data store for all downstream consumers.
2. **Why `email` must be in the skip list:** Columns NOT in the skip list go through numeric extraction (`str.replace_all(r"[,\$]", "").str.extract(r"(-?\d+(?:\.\d+)?)").cast(pl.Float64)`). This would attempt to parse email addresses as floating-point numbers, silently nullifying all 11,386 values. Adding `"email"` to the skip list preserves it as a raw String identifier — identical treatment to `Lead_ID`, `CITY`, `STATUS`, and `COUNTRY`.

### 23.1.3 Insertion Point C — Email in Graph Schema

**LOCATION:** In `ingest_data()`, the `graph_columns` list at line 379-410.

**ADD `"email"`** to the `graph_columns` list:

```python
    graph_columns = [
        "Lead_ID",
        "NAME",
        "STATUS",
        ...
        "CREATEDDATE",
        "email",          # V16-1: recovered from unstructured columns
    ]
```

**ARCHITECTURAL RATIONALE:**

1. **Why `email` must be in `graph_columns`:** The `graph_columns` list determines which columns from the sanitized DataFrame are selected for Neo4j ingestion. Without `email` in this list, it would be excluded from the `records` dict and never reach the Cypher UNWIND block.
2. **Null handling:** The graph column cleanup loop already handles null-like strings (`nan`, `none`, `null`, `na`, empty) and converts them to Python `None`. Email addresses don't contain these patterns, so they pass through unchanged. Null emails (the ~179K majority) are correctly set to `None` by this loop — matching the existing `gclid`/`google_ads_campaigns`/other optional property pattern.

### 23.1.4 Insertion Point D — Email in Cypher UNWIND Block

**LOCATION:** In `ingest_data()`, the Cypher query string at line 435-485, inside the `SET` clause.

**ADD after `l.createddate = record.CREATEDDATE`** (line 459):

```cypher
        l.createddate = record.CREATEDDATE,
        l.email = record.email,
```

**ARCHITECTURAL RATIONALE:**

1. **Why a simple SET property (not a separate FOREACH block):** `email` is a scalar property with no relational semantics — it doesn't create new nodes or edges. A `FOREACH (CASE WHEN ...)` block would be overengineering. The existing `l.gclid = record.GCLID__C` at line 442 is an identical pattern — an optional scalar property set directly on the Lead node. Null values (for ~179K leads) are silently ignored by Neo4j's MERGE/SET semantics.
2. **Why no new constraint needed:** The V16 Phase 2-A Neo4j schema extension already created `person_email_idx` (`CREATE INDEX person_email_idx IF NOT EXISTS FOR (p:Person) ON (p.email)`). The Lead node `email` property doesn't need a dedicated index — it's only used as a lookup key during `resolve_persons_to_neo4j()` which reads from parquet, not from Cypher.
3. **Why no `FOREACH` guard against null:** Unlike Location/Campaign/Industry nodes where null values would create orphan nodes, a null email is harmless — Neo4j simply stores nothing for that property. The `coalesce()` guard pattern used for relationship-creating FOREACH blocks is unnecessary for scalar properties.

### 23.1.6 Contingency Paths

| Failure | Detection | Response |
|---------|-----------|----------|
| `email-urls.csv` not found | `os.path.exists` returns False | Print nothing. Pipeline continues — identical to current behavior. No email column created. |
| `email-urls.csv` is empty or malformed | Polars `read_csv` raises exception | try/except catches it. Prints `[V16-1 Non-Critical] Email join failed: {e}`. Pipeline continues. |
| Email column at 94% null gets ghost-purged | Column not in `explicit_required_cols` before purge | NOT applicable — join happens AFTER ghost column purge. Column is safe. |
| Email column goes through numeric extraction | Not in skip list at Insertion Point B | Silently nullifies all 11,386 values. Add `"email"` to skip list. |
| Email column missing from math_columns | Not in list at Insertion Point B | `math_schema.parquet` has no email column → `person_resolver.py` returns error. |
| Email column missing from graph_columns | Not in list at Insertion Point C | Neo4j Lead nodes have no email property. |
| Cypher UNWIND has no email SET | Missing from Insertion Point D | Neo4j Lead nodes lack email property. `person_resolver.py` still works (reads from parquet). |
